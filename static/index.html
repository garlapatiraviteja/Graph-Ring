How a refund happens

1
The model explains and proposes; code decides. A refund requires a risk index of 60 or higher and a nearest confirmed fraud with similarity of at least 0.70.
2
Code rejects any number or ID in the model's text that the scorer did not produce.
3
You confirm. PayPal rejects a second full refund of the same payment.

Graph Ring

Each payment is linked to the payments most similar to it. Your few confirmed frauds pass their label along those links, so unlabelled "ghost" payments acquire a risk score. Nothing is trained. The evidence for each flag is the confirmed fraud it most resembles.

  • Known-good payment

From flag to refund in four steps

Every step is visible in the app, so you can see why a payment was flagged before any money moves.

1

Score

Graph Ring links each payment to its nearest neighbours and propagates risk from your confirmed frauds along those links.

2

Explain

A language model drafts a short explanation and proposes refund, review or approve, using only facts the scorer produced.

3

Verify

Code rejects any number or ID the scorer did not produce, then enforces the refund policy. The model cannot override it.

4

Refund

PayPal REST API

You confirm; GhostRing checks the capture with PayPal and issues the refund. A captured payment can be fully refunded only once.

Send this PayPal refund?

GhostRing integrates the PayPal REST API and issues refunds in the sandbox, with test money. It is an independent project, not affiliated with or endorsed by PayPal. Transaction features come from the anonymised ULB credit-card dataset. The risk index ranks payments; it is not proof of fraud, and every refund needs a person's confirmation.
